## SQL para Análise de Dados e Data Science

### Programação em Banco de Dados com Linguagem SQL

#### TRIGGER

- bom para executar ações com base em outras ações

```sql
CREATE TRIGGER <trigger_name>
AFTER <action_name> -- INSERT, DELETE, UPDATE
FOR EACH ROW
EXECUTE FUNCTION <name_function>
```

- não podemos criar `TRIGGER` sem criar a `FUNCTION`
  - a `FUNCTION` deve retornar a `TRIGGER`
- nos updates podemos usar o `NEW` para acessar novas transações
- funções associadas a `TRIGGER` não podem ser usadas por outros objetos do SGBD
- `TRIGGER` são associados a outra tabela, especificamente
- controle de transações

```sql
BEGIN
...
COMMIT;
-- OU
ROLLBACK;
```
- transações são atômicas, só é completa se todo o código funcionar
- independente da dimensão da lógica dentro da transação, ela é executada como uma unidade
- funções podem chamar outras funções $\to$ funções aninhadas
- a forma mais correta de executar modificações (`INSERT`, `DELETE`, `UPDATE`) não devem ser executados diretamente
  - recomendação: usar funções ou `STORED PROCEDURES` com validações
- podem capturar os erros das transações:

```sql
EXCEPTION
    WHEN <error_type> THEN
        RAISE NOTICE <msg>
        ROLLBACK
```

- se eu não quiser o usar o retorno da função posso retornar `VOID`
- se quiser retornar uma tabela, podemos usar a expressão: `RETURNS TABLE`
- variáveis `CURSOR` servem para percorrer uma lista de valores (que pode ser um `SELECT`)
  - `OPEN CURSOR` $\to$ abre a lista
  - `FETCH` $\to$ recupera os registros do cursor
  - `EXIT WHEN NOT FOUND` $\to$ fecha a lista do cursor
- podemos acessar os atributos do cursor usando ponto
  - `RETURN NEXT` $\to$ próximo item do cursor

### Qual a Importância em Otimização Consultas SQL?

- **melhoria de desempenho:** melhoria do tempo de respostas
  - para sistemas de grande volume de dados
- **redução de carga no servidor**: menos / recursos menores necessários $\to$ custos operacionais
- **escalabilidade**: lidem melhor com o aumento no volume de dados, sem degradação de desempenho
- **melhoria na utilização de índices**: acelerar a recuperação dos dados, se os índices estão corretos
- **minização de bloqueios**: diminui a chance de *deadlocks*
- **aumento na satisfação do usuário**: melhor experiência dos usuários, engajamento
- **uso eficiente de largura de banda**: minimização de latência, especialmente em ambientes distribuídos ou em nuvem

### O que é um Plano de Execução SQL?

- representação detalhada do como o SGBD vai executar a consulta SQL
  - como tabelas são acessadas
  - quais índices são acessados
  - detalhamento de filtros e joins
- um guia/roteiro da maneira mais eficiente de executar uma consulta

#### Componentes-Chave de um Plano de Execução SQL

1. **operação de acesso**: como os dados são acessados; *full table scan* $\times$ índices
2. **métodos de junção**: como tabelas são combinadas: junção *hash*; *nested loops*
3. **ordem de execução**: sequência de operações, incluindo filtros
4. **estimativa de custos**: custos relativos de diferentes partes da consulta
   1. CPU; memória, operações de disco
      1. ajudam a escolher entre diferentes planos possíveis
5. **estratégias de ordenação `ORDER BY` e agrupamentos `GROUP BY`**

- otimização de consultas: identificar problemas no plano de execução e modificar a query para resolver/mitigar gargalos de performance
- exibir o plano $\to$ `EXPLAIN`

#### Uso de Índices

- melhorar a eficiência das operações de leitura
  - catálogo / mapa para ajudar o banco de dados a encontrar as linhas que correspodem aos critérios consultados
  - sem índices, SGBD teria que escanear todas as linhas para encontrar os dados desejados

##### Considerações a Respeito dos Índices

- **Overhead de Manutenção**: precisam ser atualizados nas inserções, atualizações ou exclusões $\to$ desempenho de escrita prejudicado
- **Uso de espaço**: armazenamento adicional requerido
- **Seleção de colunas**: nem todas são candidatas  ideais para indexação
  - colunas com baixa cardinalidade podem não se beneficiar tanto
- **Design de Índice Composto**: atenção na ordem das colunas
  - a coluna mais usada devem vir antes

##### Tipos de Índices

- **índice B-tree**: mais comum, buscas por igualdade, consultas por intervalo, ordenações
  - mantém os dados ordenados
  - pesquisas, inserções, e excluões em tempo logarítmico
- **índice hash**: melhor para buscas por igualdade; não é eficiente para buscas por intervalo
- **índice GIST (Generalized Search Tree)**: para tipos de dados complexos; geometria e dados de texto completo
- **índice GIN (Generalized Inverted Index)**: indexar elementos dentro de dados complexos
  - arrays, documentos de texto 
  - cada elemento indexado como uma entrada completa
- **índice BRIN (block range IN)**: resumos de valores armazenados em blocos de dados consecutivos
  - ideais para dados naturalmente ordenados ou sequenciais

##### Quando Usar Índices

- colunas frequentemente usadas em cláusulas `WHERE`
- colunas usadas em operações `JOIN`
- colunas usadas para ordenação e agrupamento de dados (`ORDER BY`, `GROUP BY`) $\to$ evitar a necessidade de reordenar os dados cada vez que a consulta é executada

### Particionamento de Dados

- gerenciar tabelas grandes
- dividir uma tabela grande em partes menores
  - mais gerenciáveis
  - otimizar operações de leituras/escritas, manutenção, recuperação de dados
- baseado em múltiplos critérios
  - intervaloes de datas, valores de chaves; localizações geográficas (particionamento por intervalo)
  - particionamento por lista $\to$ baseados em conjuntos específicos de valores
    - útil quando o conjunto de valores é discreto (categorias de produtos ou regiões geográficas)
  - particionamento por *hash* $\to$ quando não há um critério natural de intervalo ou lista, distribuição uniforme dos dados
- **Benefícios do Particionamento**
  - melhoria no desempenho de consultas $\to$ filtro com base na chave do particionamento
  - manutenção eficiente $\to$ `VACUUM`, `ANALYZE` e backups realizados com partições individuais, redução de impacto na disponibilidade
  - inserções, atualizações, e exclusões rápidas $\to$ especialmente para operações com grandes volumes
  - otimização do armazenamento $\to$ gestão de recursos mais eficaz
- **Cuidados ao Implementar Particionamento**
  - escolha da chave de particionamento $\to$ refletir padrões de acesso
  - balanceamento de partições $\to$ desbalanceamento de carga é ruim
  - gerenciamento de partições $\to$ pode ser declarativo; plenejar e monitorar o esquema de particionamento
    - evitar complexidade desnecessárias
    - garantir requisitos de desempenho
- compatibilidade de consultas e índices $\to$ consultas e índices devem ser projetados considerando o esquema de particionamento
  - índices locais (dentro das partições)
  - índices globais (abrangendo todas as partições)
- evitar consultar todas as colunas SQL de uma tabela (*) $\to$ filtragem excessiva
- evitar `CROSS JOIN` $\to$ principalmente para tabelas grandes
- sempre indispensável olhar o plano de execução para realizar a otimização da query
- filtragem redundantes $\to$ custo adicional de processamento
- desconsiderar índices $\to$ observar filtros para criar índices
- ordenações por múltiplas colunas
