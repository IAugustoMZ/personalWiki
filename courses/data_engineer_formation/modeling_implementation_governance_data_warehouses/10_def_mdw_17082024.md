### Backup e Recuperação de Dados do DW

- ferramentas de gestão
- recuperação de dados
- diversos de tipos
    - **completo**: cópia completa de todos os dados
        - simples de executar e recuperar
        - consumo alto de tempo e espaço
    - **incremental**: apenas as aleterações feitas no último backup
        - menor consumo de tempo e espaço
        - processo mais complexo -> restauração de vários backups incrementais
    - **diferencial**: mudanças feitas desde o último backup completo
        - mais rápido que um modelo totalmente incremental
        - só requer o último backup completo e o último incremental
        - pode crescer rapidamente em tamanho, dependendo da taxa de alteração dos dados
    - **snapshot e replicação dos dados**: funcionalidade de armazenamento para capturar snapshots de dados em intervalos regulares ou replicar dados para um local remoto
        - recuperação rápida ou voltar num ponto anterior do tempo
        - dependente de infraestrutura de armazenamento
        - pode não ser tão flexível
    - **backup em nuvem**: serviços de armazenamento para armazenar backups, proporcionando escalabilidade e flexibilidade
        - redução de hardware local
        - escalabilidade
        - recuperação de desastres
        - dependente da conexão da internet
        - custos variáveis
    - **high availability**: sistemas que mantêm cópias dos dados operacionais que podem ser rapidamente ativados em caso de falhas
        - minimiza o tempo de inatividade e perda de dados
        - mais caro de implementar e manter

### Estratégias de Recuperação

- **plano de recuperação de desastres**: especifica como os dados serão restaurados após uma falha
    - local de armazenamento após uma falha
    - responsabilidade
    - processos para verificar integridade

- **testes de restauração**: garantir que os dados podem ser efetivamente restaurados dentro de uma janela de tempo aceitável e com integridade

### O que é Slowly Changing Dimensions (SCD)?

- conceito usado para gerenciar e tratar dados que mudam lentamente
    - lidam com as mudanças nas dimenões de maneira controlada e sistemática

- principais tipos
    - *tipo 1* -> dados antigos são sobrescritos com os dados. Não há histórico
        - simples
    - *tipo 2* -> mudanças nos dados são rastreadas criando-se uma nova linha para cada alteração com um novo identificador
        - marca a linha antiga como inativa ou obsoleta
    - *tipo 3* -> histórico limitado, mantendo apenas o valor atual e o anterior em colunas separadas
        - útil para rastrear algumas mudanças sem manter um histórico completo
    - *tipo 4* -> cria uma tabela de histórico (outra dimensão)
    - *tipo 5* -> combina os tipos 2 e 3.

#### Implementando SCD - tipo 1

- **atualização**: o valor antigo é simplesmente sobrescrito pelo novo. Não há preservação do histórico de mudanças
- **simplicidade**: mais simples de implementar
- **cenários de uso**: quando o histórico de alterações não é importante, ou quando é necessário manter apenas o valor mais recente
- não permite análises históricas profundas

#### Implementando SCD - tipo 2

- manter histórico completo de mudanças ao longo do tempo
    - rastreamento de todas as dimensões
- **histórico completo**
- **surrogate keys** -> identificação única e não ambígua (várias versões do mesmo item)
- **campos de controle de versão** -> identificação dos períodos, e qual é o atual
- **gestão das mudanças** -> quando um novo valor é adicionado, as modificações são automatizadas
- análises de tendências ou rastreamento do histórico são importantes
    - registros precisos para conformidade regulatória ou auditorias
- atributos que mudam frequentemente e de maneiras significativas
    - preservação dos estados é importante
- aumento substancial da base
    - complexidade das consultas

#### Implementando SCD - tipo 3

- projetado para preservar um histórico limitado
    - estado atual e um estado anterior
- **armazenamento limitado de histórico**
- **simplicidade e eficiência**: mais simples e menos pesado que SCD tipo 2 (menos dados históricos)

### Definindo o Processo ETL vs ELT

- ETL -> extração, transformação e carregamento
- ELT -> extração, carregamento e transformação

#### Diferenças e Escolha

- **performance**: ELT tende a ser mais rápido para grandes volumes de dados
    - potência de processamento dos sistemas de armazenamento moderno
- **flexibilidade**: ELT oferece mais flexibilidade, transformação de dados sem a necessidade de reprocessar a carga
- **segurança e conformidade**: ETL preferível quando dados precisam ser limpos e transformados antes de serem armazenados

#### Traditional ETL x Modern Data Stack ETL

|                     | **ETL Tradicional**                | **Modern Data Stack ETL**         |
|---------------------|------------------------------------|-----------------------------------|
| **Ferramentas**     | On-premises, instalação e manutenção  significativas | Cloud-based, Integração fácil |
| **Processamento**     | processamento em ambiente separado, geralmente antes dos dados serem carregados -> gargalos     | Foco em flexibilidade, escalabilidade automática e manutenção reduzida, transformações antes ou depois da carga |
| **Custo e Escalabilidade** | limitada pelo hardware local, custos com infraestrutura | Baseado no uso, escalabilidade gerenciada pelo provedor de serviços (elasticidade), custo-efetividade |
| **Atualização e Manutenção** | Esforço considerável | Reduz a carga de gerenciamento |

##### Considerações para Escolha

- custos operacionais vs iniciais
- complexidade dos dados
- requisitos de conformidade e segurança
    - ETL dá mais controle
- necessidade de agilidade e escalabilidade em ambientes de dados mais complexos e volumosos
- é comum haver uma camada de staging no meio
    - Banco Tradicional -> Staging Area -> Data Warehouse
- Airbyte é uma ferramenta de transporte de dados
