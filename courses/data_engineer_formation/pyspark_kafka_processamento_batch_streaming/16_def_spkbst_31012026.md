## PySpark e Apache Kafka para Processamento de Dados em Batch e Streaming

### Multi-Node Cluster Spark, HDFS e Kafka

#### Compreendendo os Conceitos de Broker e Controller no Kafka

- **Broker:** servidor responsável por armazenar e distribuir os dados (mensagens) que trafegam no sistema
  - gerenciam os tópicos e particionam os dados para garantir alta disponibilidade e escalabilidade
  - mantêm um subconjunto de partições dos tópicos (armazenamento consistente de mensagens)
  - enviam dados para os consumidores (*publish-subscribe*)
  - adicionar mais brokers aumenta a capacidade de armazenamento e processamento
  - os dados são replicados enter os brokers para garantir resiliência no caso de falhas
- **Controller**: papel desempenho por um broker específico
  - eleito dinamicamente, responsável por coordenar operações
  - **gerenciamento de partições:** decide qual broker será o líder de cada partição (líder: processar todas operações de leitura ou escrita)
  - **detecção de falhas:** monitoramento de estado, redistribuição de partições
  - **sincronização de replicas:** controle de sincronia
  - **coordenação de tarefas de manutenção:** suspensão de operações administrativas, reconfiguração de tópicos ou exclusão de dados

- **interação entre broker e controller**
  - brokers são responsáveis por armazenar e manipular os dados, enquanto que o controller atua como um coordenador
    - garantir que o cluster funcione de maneira organizada
  - quando um broker falah, o controller detecta a falha e reorganiza o cluster
    - promoção de novos líders para as partições

#### Zookeeper $\times$ Apache Kafka Raft (KRaft)

- tecnologias relacionadas à coordenação e gerenciamento do cluster

##### Zookeeper no Apache Kafka

- ferramenta externa de coordenação distribuída para gerenciar
  - metadados do cluster, tópicos, partições e réplicas
  - liderança de partições
  - detecção de falhas e monitoramento do broker
  - configuração dinâmica: registros das configurações e mudanças de estado
- **limitações**
  - dependência externa: cluster zookeeper separado (aumenta a complexidade de implementação, configuração e manutenção)
  - latência: comunicação entre Kafka e Zookeeper
  - arquitetura não unificada: dificuldades na manutenção de um sistema externo e mais suscetível a falhas ou problemas de sincronização

##### Apache Kafka Raft (KRaft)

- Raft $\to$ protocolo consenso distribuído projetado para simplicidade e eficiência, garantindo eficiência de réplicas
  - coordenador embutido: Kafka gerencia os próprios metadados internamente
  - liderança e replicação: eleição de líderes e sincronia de metadados entre brokers (alta disponibilidade e consistência)
  - arquitetura simplificada: brokers Kafka atuam como controllers tendo as mesmas funções do Zookeeper

##### Por que usar o Apache Kafka Raft (KRaft) é melhor?

- arquitetura unificada $\to$ elimina a dependência de um sistema externo
- desempenho melhorado $\to$ latência reduzida (operações mais rápidas, especialmente em tarefas administrativas)
- manutenção simplificada $\to$ direto
- maior resiliência $\to$ protocolo Raft projetado para lidar eficientemente com falhas de nós garantindo uma recuperação mais rápida e confiável
- preparação para o futuro $\to$ padrão de coordenação a partir de versões mais recentes (mais compatibilidade)
- escalabilidade aprimorada $\to$ mantendo consistência e desempenho

- planejar a migração do Zookeeper é sempre recomendado em caso de clusters existentes
  - usar KRaft no caso de novos clusters criados do zero
