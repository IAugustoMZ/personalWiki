#### Estratégias de Backpressure e Rate Limiting

-  uso de duas tabelas em streaming
   -  salvar entrada
   -  salvar a saída do modelo
-  tomar cuidado com conexões para banco de dados
   -  considerar latência
-  detecção de anoamlias por autoencoders, pode ser feita por análise do erro de reconstrução
-  sempre que vamos estabelecer um limite / threshold / hiperparâmetro
   -  documentar a decisão de projeto $\to$ isso impacta o negócio e precisamos ter visibilidade
-  leitura do streaming $\to$ conexão via socket
   -  *read Spark Streaming*
-  aplicação de `VectorAssembler` para gerar dados vetorizados
-  passar cada batch extraído da fonte em tempo real, para a função de detecção de anomalias
-  persistência não é obrigatória, mas se não fizermos, todos os dados serão perdido quando fecharmos a sessão do Spark
-  podemos configurar a aplicação para enviar notificações do caso da detecção de anoamlias
-  se fazemos persistência, podemos acessar o banco de dados para realizar análises ad-hoc dos resultados
   -  análises, dashboards
  
### Multi-Node Cluster Spark, HDFS e Kafka

#### Quando usar o Apache Kafka?

- plataforma de streaming de dados distribuída e em tempo real
  - pipelines de dados em tempo real
  - sistemas de streaming $\to$ publicação, armazenamento e processamento contínuo de dados em grandes volumes
- sistemas de baixa latência, escalabilidade e processamento contínuo de eventos
- processsamento de fluxo em tempo real
  - interações de usuários em sites e aplicativos
- integração de dados $\to$ conexão de diversas fontes num único repositório central
- monitoramento de logs de eventos
- filtragem e roteamento de eventos $\to$ *middleware* entre muitas aplicações consumidoras
- cargas de trabalho de IoT $\to$ gerenciar o fluxo contínuo de dados de dispositivos conectados
- arquiteturas de microsserviços

#### Arquitetura do Apache Kafka

- **Producer:** enviam os dados para o Kafka, para tópicos específicos
  - detalhes configuráveis (particionamento)
- **Consumer:** leem os dados do Kafka (tópicos)
  - inscrição nos tópicos, e processamento dos dados
  - organizados em grupos, cada consumidor de um grupo lê de uma partição para evitar redundância na leitura de dados
- **Broker:** servidor que armazena e recebe os dados dos producers, além de disponibilizá-los para o consumers
  - *cluster:* múltiplos brokers, trabalho em conjunto para distribuir a carga e garantir disponibilidade
    - cada broker armazena dados de várias partições e é identificado por ID único
- **Zookeeper ou Kafka Controller:** versões mais antigas do Kafka, responsável pelo gerenciamento da coordenação entre brokers
  - manutenção de metadados
  - controle do balanceamento de carga
  - nas versões mais recentes $\to$ KafkaController (elimina a necessidade de um componente externo e aprimora a escalabilidade e simplicidade do sistema)
