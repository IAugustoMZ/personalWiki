##### Criação de Pipelines com Delta Live Tables

- usar Airbyte para integrar o ambiente local (PostgreSQL) para o ambiente de nuvem (Databricks)
- opções de autenção envolvem OAuth ou Personal Access Tokens
  - PAT $\to$ demanda a atualização dos tokens a cada 90 dias
- performance do Airbyte pode ser afetada pela quantidade de aplicações em exeucação
- Airbyte oferece diferentes modos de sincronização:
    1. **sincronização completa (full refresh)**
       1. **append**: lê todos os dados da fonte e os adiciona ao destino, sem substituir os dados existentes
          1. múltiplas cópias dos mesmos registros no destino
       2. **ovewrite**: substitui completamente os dados no destino
          1. útil quando se deseja uma cópia exata da fonte no destino
    2. **sincronização incremental**:
       1. **append**: apenas dados novos ou modificados desde a última sincronização
          1. não altera ou remove dados existentes
          2. pode resultar em múltiplas versões do mesmo registro no destino
       2. **append + dedup**: similar ao append, mas mantendo uma versão deduplicada dos dados
          1. usa uma chave primária para garantir apenas a versão mais recente de cada registro
- para sincronização incrementa, precisamos definir um campo para ser utilizado como cursor
  - o cursor marca quais modificações sçao incrementar em relação à última atualização
- é possível realizar sincronismo entre as fontes de dados
  - pode ser inclsuive que uma aprovação é necessária
- o primeiro sincronismo pode ser mais demorardo pois o ambiente de computação e novo schema precisa ser criados e inicializados
- o Airbyte pode enviar metadados sobre cada coluna
- dados podem ser também carregados manualmente no Databricks
  - casos pontuais, onde o volume de dados pode ser pequeno e não vale a pena usar coisas mais complexas
- quando deixamos o ambiente ocioso, o próprio Databricks desliga para gerar economia
- podemos modificar quais sados serão moviemntados da fonte para o destino
  - mesmo se haver novas colunas, que podem ser adicionadas posteriormente
- Databricks oferece suporte a múltiplas linguagens
  - Pytho, Scala, SQL, R
- Databricks Connect $\to$ ambientes de desenvolvimento integrados
  - Visla Code, PyCharm, RStudio, IntelliJ
  - facilita o desenvolvimento e depuração de código direto no Databricks
- podemos implementar os pipelines em um notebook
  - cada notebook pode estar associado a um ambiente diferente (cluster)
  - SQL Warehouse $\to$ só suporta execução de código SQL
- no notebook, é importante especificar o catálogo e o schema a serem utilizados
- durante a execução do código, todos os códigos são executados num cluster Spark executado na nuvem $\to$ dá para reproduzir localmente com um cluster Spark, mas há um custo de infraestrutura associado
- é possível também criar gráficos usando o pySpark + matplotlib
- DataFrame Spark $\to$ otimizado para ambientes distribuídos
- todos os resultados intermediários são salvos na memória do cluster
  - perdidos se fecharmos o notebook ou desligarmos o cluster
  - podemos salvar os resultados importantes de volta no catálogo
- para acessar o sample de dados no catálogo, precisamos ter um recurso de computação ativado
- geralmente o custo de se manter um ambiente Databricks é menor do que construir e manter uma infraestrutura equivalente
