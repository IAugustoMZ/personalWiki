### MLOps Essentials: Para Portfolios de Projetos, Gestão de Código e Dados com Git e DVC

#### Commits Semânticos e Histórico Limpo

- *commit* $\to$ registro permanentes de um conjunto de alterações feitas no projeto
  - ponto no histórico que captura o estado dos arquivos versionados após modificações
  - mudança realizadas, mensagem descritiva, metadados como autor e data
    - execução do projeto, reverter alterações, compara versões e entender o contexto técnico de cada mudança
- estrutura básica: `<tipo>(<escopo opcional>)<descrição breve>`
  - `feat`: uma nova funcionalidade
  - `fix`: correção de um bug
  - `docs`: apenas documentação
  - `refactor`: mudança no código que não altera funcionalidade
  - `chore`: tarefas de manutenção
- pensar sempre na atomicidade do commit
  - commits menores e focados

Exemplo de um commit pequeno e descritivo:

```bash
git status
git add src/train.py tests/test_train.py
git commit -m "feat(training): add reproducible model training"
```

Antes de publicar, o histórico pode ser revisado sem alterar os arquivos:

```bash
git log --oneline --decorate -5
git show --stat HEAD
```

#### Branches e Fluxo de Trabalho (*Feature Branch Workflow*)

- main $\to$ ramo principal do repo
  - código mais estável e confiável do projeto
- outras branches criadas a partir da main
  - interações após revisões e validações
- trabalho direto da main = má prática
  - *feature branch workflow*
    - main deve conter um código estável, pronto para produção
- branches são boas para testes A/B de modelagem

Um fluxo mínimo para uma mudança isolada pode ser:

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/experiment-logging
# implementar, testar e revisar
git push -u origin feat/experiment-logging
```

#### Iniciando o DVC

- assim que é iniciado (`dvc init`), novos arquivos de configuração são gerados
  - pequenos arquivos de texto e devem ser commitados no git

##### Rastreando Datasets Grandes

- metafiles $\to$ ponteiros 

```bash
dvc add data/raw/dataset_gigante.csv
```
- calcula o hash (MD5) do arquivo para criar uma impressão digital única
- move o arquivo real para o cache do dvc (oculto) e deixa um link simbólico (ou cópia) na pasta original para você trabalhar
- adiciona o arquivo original ao `.gitignore`
- cria um arquivo pequeno chamado `dataset_gigante.csv.dvc` $\to$ este é o ponteiro
  - pesa alguns bytes e tem metadados sobres o hash e sobre o tamanho do arquivo original

##### Configuração do Remote Storage

- onde o dvc salva dados e arquivos pesados
  - sem isso, os dados versionados ficam presos na máquina local
- agnóstico à nuvem
  - só precisamos apontar o caminho do storage remote

```bash
dvc remote add -d my_remote_drive...
git add .dvc/config
```

- fluxo de trabalho alinhado ao git
  - `git push / dvc push`
  - `git pull / dvc pull`

Depois de configurar o remote, o ciclo de publicação fica explícito:

```bash
dvc push                 # envia os dados para o armazenamento do DVC
git push origin main     # envia código, configuração e ponteiros
```

##### Data Registry (Registro de Dados)

- muitas cópias e colas do mesmo arquivo causam o caos do versionamento
  - data registry: "loja de aplicativos" de dados
    - importação do dado diretamente do registro do dvc, sem necessidade de baixar o csv manualmente
- `dvc update` $\to$ baixa os dados mais atualizados automaticamente
- fluxo "data mesh" $\to$ dados como produto

##### De Notebooks para Scripts Modulares

- Jupyter notebooks não são a opção ideal para ambiente de produção
  - problema do "estado oculto" $\to$ executar fora de ordem
  - dificuldade de versionar (diffs são ilegíveis)
- refatoração $\to$ quebrar o monólito do notebook em scripts Python modulares e com responsabilidades únicas
  - `src/data_load.py` $\to$ apenas baixa e salva o dado bruto
  - `src/featurization.py` $\to$ lê o dado bruto, limpa cada feature, salva o dado processado
  - `src/train.py` $\to$ lê o dado processado, treina o modelo e salva o arquivo .pkl (ou simular)
  - `src/evaluate.py` $\to$ lê o modelo de e dados de teste, e gera métricas de performance

- modularização melhora a colaboração do time, reduz conflitos, facilita a criação de testes unitários

##### Criando o DAG (Grafo Acíclico Dirigido) com DVC

- precisamo orquestrar os scripts modularizados
- podemos usar o `dvc.yaml` para descrever as etapas (stages) do pipeline, declarando explicitamente:
  - comando a ser executado
  - dependências (deps): quais arquivos o script precisa para rodar
  - outputs: o que o script gera
- dvc cria um mapa mental do projeto, criando uma coluna inquebrável e auditável
  - fluxo de daods é transparente e documentação no código

Exemplo de um `dvc.yaml` declarando dependências e saídas:

```yaml
stages:
  train:
    cmd: python src/train.py
    deps:
      - data/processed/train.parquet
      - src/train.py
    params:
      - train.learning_rate
    outs:
      - models/model.pkl
```

##### Executando Pipelines com dvc repro

- vantagem da DAG $\to$ "inteligência da execução"
- comando dvc repro (reproduzir) $\to$ Memoization (cache inteligente) para o ML
  - verificação do estado atual de cada dependência (pelo hash do arquivo)
  - se apenas o script de treino for alterado, o dvc pula a etapa da limpeza dos dados (pois os dados e os scripts de limpeza de limpeza estão intactos) e apenas treino e execução são executados
  - se mudou o dataset bruto, dvc detecta a mudança na base da cadeia e reexecuta tudo
- economiza horas de computação e garante a integridade

Para reproduzir apenas as etapas afetadas e inspecionar o resultado:

```bash
dvc repro
dvc metrics show
dvc diff
```

##### Versionamento de Experimentos (Métricas e Parâmetros)

- rastreando nativo de parâmetro de dvc
- **`params.yaml`**: arquivo central onde definimos hiperpaâmetros. scripts Python lêem valores desse arquivo ao invés de tê-los hard-coded
  - dvc rastreia isso como dependência
- **métricas**: não apenas printar no terminal mas armazenar em um arquivo JSON ou texto
- permite execução de múltiplos experimentos verariando `parametros.yaml`, executando `dvc repro`
  - histórico auditável de qual configuração gerou qual resultado, tudo versionado no git
- README perfeito $\to$ explicar como executar o projeto de forma rápida e concisa

##### Colaboração em Equipe

1. `dvc push` $\to$ envia arquivos pesados para o remote storage
2. `git push` $\to$ envia os códigos e ponteiros `.dvc` atualizados para o github
3. `git pull` $\to$ baixa o código atualizados e os ponteiros atualizados
4. `dvc pull` $\to$ atualiza arquivos de dados atualizados do remote storage

##### Checklist de Auditoria

- **reprodutibilidade zero-touch**: se eu apagar a pasta models e rodar `dvc repro`, o sistema reconstroi tudo sozinho?
- **segredos protegidos**: existe algum arquivo `.env` ou chave de API commitada por engano?
  - verifique o histórico, não apenas o arquivo atual
- **isolamento**: existe um `requirements.txt` ou `pyproject.toml`? O projeto depende de bibliotecas instaldas globalmente na máquina do usuário?
- **limpeza**: o código tem variáveis não utilizadas, prints de debug (`print("...")`) ou células de notebook comentadas?
- **semântica**: as mensagens de commit contam uma história ou são apenas "updates"?
- **dados**: os arquivos pesados estão realmente fora do git (listados no `.gitignore`)

#### Próximos Passos em MLOps: Introdução a CI/CD

- transição de fluxos manuais para automação contínua de ponta a ponta
  - desenvolvimento, validação, e implantação de modelos de forma sistemática
- CI/CD passa a orquestrar todo o ciclo de vida de Machine Learning
  - cada alteração no código ou nos dados deve disparar pipelines automatizados capazes de reproduzir ambientes, executar testes, treinar modelos e validar resultados de maneira consistente
- repositório $\to$ papel de fonte única da veradde
  - versionamento de dados e experimentos assegurando reprodutibilidade e rastreabilidade técnica
- ferramentas de automação nativas de plataformas de versionamento
  - GitHub Actions permitem a execução dos pipelines em infraestrutura efêmera na nuvem
- dvc e o CML complementam o CI/CD tradicional ao incorporar dados e métricas de modelo no fluxo
  - avaliações automáticas e feedback estruturado sobre desempenho
- modelos testados, comparados e preparados para produção de forma contínua, confiável e auditável
  - escalabilidade e governança em ambientes de IA

Um job de CI pode transformar essa ideia em uma verificação automática:

```yaml
name: quality

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest
```
