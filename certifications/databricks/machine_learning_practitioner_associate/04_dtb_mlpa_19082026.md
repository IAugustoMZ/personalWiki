## Introduction to Data Preparation for Machine Learning

### Data Preparation and Feature Engineering

#### Data Standardization

- Spark ML Pipeline chains multiple transformation and estimation steps into a single, reproducible workflow
  - applying each step manually risks inconsistencies between training and test data
  - pipelines ensure the exact same transformation are learned from training data and then applied uniformly to new data
    - important for steps like imputation and scaling where statistics are used for transformations and must be derived from training data only (prevent data leakage)
- the order matters $\to$ each stage depends on the output of the previous
- final ``VectorAssembler`` combines the scaled numerical features and the one-hot  encoded categorical vectores into a single feature vector
  - SparkML models expect all input features to be packed into one vector column
- fitting the pipeline on the training data runs each ``Estimator`` stage to learn its parameters
  - learned parameters are stored in the resulting `PipelineModel` and reused consistently when transforming new data
- a `PipelineModel` is an object that can be saved to disk, loaded from it and reused on new data

### Introduction to Feature Store

- manages features, or input data to a machine learning model $\to$ created through feature engineering
  - aggregations of raw data over time windows
  - joined combinations of data sets
  - complex functions evaluation results
- **basic motivations**
  - **discovery**: multiple data scientists are trying to solve similar modeling tasks and come up with different definitions of the features
  - **lineage**: model governance requires documentation of the features used to train a model
    - upstream lineage of a feature to reliably use it
  - **skew**: when multiple teams manage feature computation an ML in production minor yet significant skew in upstream data at the feature pipeline cvery hard to detect and find
  - **online servig**: during exploration and model experimentation phases are implemented in frameworks that do not scale to production
- feature store is now integrated as part of the Unity Catalog
  - feature engineering client  Python API allows the incorporation of Data Ops practices into feature engineering pipeline and interact with or create feature tables
- how does Databricks Features Store work?
  - write code to convert raw data into features and create a Spark Data Frame containing the desired features
  - save features to feature tables that are based on Delta Lake supporting ACLs, versioning, performance optimization
    - feature tables can be used for model tranining, batch inference and real-time inference
- feature store integrates fully with Unity Catalog
  - meaning any UC table can be used as a feature table
  - feature tables behave like regular UC tables but include additional metadata for feature management
    - feature tables description matches the table content
    - feature table schema matches the table schema
  - follows the three-level namespace convention
    - catalog, schema, table
    - ensures consistency across the platform
  - uses Unity Catalog's permission model to manage access to both feature data and metadata
    - same security and governance rules for other UC tables also apply to feature tables
    - any future updaetes to UC governance capabilities will automatically extend to feature data
    - specific priviledges are granted to different user groups
- Feature Store lineage is fully integrated with Unity Catalog lineage
  - feature tables, their source data, downstream usage can all be tracked in one place
  - helps trace how data flows - from raw inputs through transformations to the final feature tables and models
  - better understanding of dependencies and ensure consistency across the workflows
- integrates with both MLflow and ModelServing to support model deployment
  - **with MLflow**: when features from Feature Store are used during training, the model is packaged along with the feature metadata
  - at inference time, the model can look up the required features using that metadata
  - **with ModelServing**: when a model is deployed for batch or online inference, it automatically retrieves the needed features from the Feature Store

| **Workspace FS** | **Unity Catalog FS**
| --- | --- |
| - specific to a single workspace<br>- challenges in sharing features tables across workspaces<br>- uses `FeatureStoreClients` to create feature tables | - any Delta table with a primary key can be a feature table (DBR 132)<br>- all UC capabilities are available, discovery, governance, lineage and cross workspaces access<br>Uses `FeatureEngineeringClient` to create feature tables |

- for small datasets, partitioning is not recommended but is recommended for high cardinality production data
- Features tab open feature store panel
  - anyone with access to the same catalog can discover the feature store table
- feature tables can be loaded programmatically in a notebook
- we can add or remove features from a feature store table
  - to delete, we need to set Delta read and write protocol version manually to support column mapping
- since the tables are based on Delta, we get all features of it including versioning
  - time travel
- we can promote existing UC tables to become feature table
  - add a primary key with non-null constraint (with timestamp if applicable)
- if you have a classic / workspace feature table, you can migrate to UC feature catalog
  - upgrade the table UC supported table
  - then use `UpgradeClient` to complete the upgrade

**1. Why is it considered a best practice to add an indicator column (e.g., `age_imputed = 1`) when performing data imputation?** - It enables transparency, allowing evaluation of imputation impact and easier error identification

```python
# Preserve whether age was observed before filling nulls; this lets analysis
# distinguish measured values from estimates and test whether missingness matters.
from pyspark.sql import functions as F
age_median = train_df.approxQuantile("age", [0.5], 0.01)[0]  # Learn from train only.
prepared = raw_df.withColumn("age_imputed", F.col("age").isNull().cast("int"))

```

**11. Which two of the following are valid strategies for handling a categorical feature with high cardinality before encoding? (Select two)** - Group rare or infrequent categories into a single "Other" category; Keep only the top-N most frequent categories and group the rest

from pyspark.sql import functions as F
# Determine the top categories from train only so test frequencies do not
# influence feature preparation; map the long tail to a shared bucket.
top_values = [r["product_code"] for r in train_df.groupBy("product_code").count()

**16. When a dataset contains outliers in numeric features, which Spark ML scaler is the most appropriate choice and why?** - ``RobustScaler``, because it scales using the interquartile range (IQR) and is less sensitive to extreme values

```python
from pyspark.sql import functions as F
# Robust scaling centers at the training median and divides by its IQR.
# Estimate parameters from train only and reuse them for every later dataset.
q1, median, q3 = train_df.approxQuantile("transaction_amount", [0.25, 0.5, 0.75], 0.01)
iqr = q3 - q1
if iqr == 0:
    raise ValueError("IQR is zero; inspect this feature before scaling")
scaled = scoring_df.withColumn("amount_robust", (F.col("transaction_amount") - F.lit(median)) / F.lit(iqr))
```
