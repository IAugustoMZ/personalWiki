### Architecting MLOps Solutions

#### Opinionated MLOps Principles

##### The Guiding Principle

- **A Data Centric approach to ML**
  - integration of data pipelines throuighout ML projects
    - aligned to Data Intelligence Platform - centralized data storage and sharing with unified security and governance
  - ML projects are made up of data pipelines
  - operationalizing ML solutions requires connecting a *varitey of data pipelines*
    - data preparation
    - feature engineering
    - model training
    - tuning
    - inference
  - data pipelines require storage, governance, orchestration
  - make data accessible, reliable, and  governed
    - reduces complexity, boosts productivity
    - focus in building robust models and pipelines
- **Multi-Environment Semantics**
  - optimize and secure workflows
  - all operate on the same assets: code, data, models
  - *development*: environment for exploration, experimentation, development
    - EDA, writing and refining ML code, initial model training and evaluation
  - *staging*: ML pratictioners can test their solutions
    - unit, integration, regression tests
    - focus in validations, transition only after all tests pass
  - *production*: ML engineers can deploy and monitor the solutions
    - deployment into a live setting, plus ongoing monitoring and periodic retraining to maintain or enhance performance

  - clear structured workflow, ensure the code and models are throughly tested and validated before deployment
    - reduces risks and support reliable, maintainable solutions

#### Environment Separation

**Direct Separation** | **Indirect Separation**
--- | ---
completely separated Databricks | one Databricks workspace with enforced separations (access controls \& naming conventions)
simpler individual environments | simpler overall infrastructure, fewer permissions
scales well to multiple projects | more complex individual environments
more setup and distinct permissions per workspace | doesn't scale well to multiple permissions
ideal for larger teams and multiple projects, ensuring isolation and scalability | simplifies infrastructure for small teams or projects, making it easier to learn and manage

#### Deployment Patterns

**Deploy Model** | **Deploy Code**
--- | ---
model is trained in the development environment | code is developed in the development env
model artifact is move from staging trough production | code is tested in the staging env
a separate process is needed for other code (inference, monitoring, operational pipelines) | code is deployed in the production env
suitable when model training is expensive or hard to reproduce | the training pipeline is run in each env, the model is deployed in production
--- | Databricks recommends this for most situations

- with *deploy code* the model is trained in each environment
  - starting in development for model development
  - staging for integration tests on a limited subset of data
  - in production or the full production data to produce the final model
- **benefits of deploy code**: access to production data is restricted, and enables *safer automated model retraining*
  - training code is reviewed, tesed, and approved for production
  - main disadvantage: steeper learning curve for data scientist to hand off code to collaborators
- **hybrid approach**: when a solution requires training the model in staging over the full production dataset
  - code is depĺoyed to staging, the model is trained there, and then the model is deployed to production
