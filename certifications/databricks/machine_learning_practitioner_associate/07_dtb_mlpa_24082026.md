## Machine Learning Model Development


### Hyperparameter Tuning Fundamentals

- hyperparameters are chosen by the practitioner or by a search algorithm
  - often a search strategy is needed
- main search methods
  - **grid search**: exhaustive brute force search, tries every combination from a predefined grid $\to$ use only when then search space is small
    - evaluates and places the best
    - computationally expensive
    - scales poorly with dimensions
  - **random-search**: random sampling of combinations samples combinations from specified distributors
    - more efficient than grid search
    - better coverage of search space
    - no guarantee of finding the best
    - better default for medium sized search spaces
  - **Bayesian optimization**: adaptative, model-based search, uses results from previous trials to decide what to try next
    - most efficient (fewer trials)
    - focuses on promising regions (based on past trial results)
    - more complex to implement
    - Tree of Parzen Estimators is a common implementation and the default algorithm of `Optuna`
      - surrogate model (probability model) of the objective model

### Validation and Cross-Validation

- validation ensures that hyperparameters do not lead to overfitting
- standard solution $\to$ 3-way split
  1. for each candidate set of hyperparameters, a model is trained on the training set and evaluated on the validation set
  2. the best hyperparams are selected based on validation performance
  3. model is retrained on the combined training + validation data, and evaluated once on the test set for a final, unbiased performance estimation
- **Limitations**
  - not enough data: splitting into training, validation, and test sets can leave each set too small
  - non-random splits: model may overfit to patterns unique to one subset
    - reduced generalizability
  - single validation set: misleading estimate of performance

#### K-Fold Cross Validation

- training data is split into $k$-subsets
  - model is trained and validated $k$ times
  - each time, using a different fold for validation and the remaining folds for training
    - produces $k$ independent estimations of validation performance $\to$ more reliable measure of generalizability

$$E_{avg} = \frac{1}{k}\sum_{i=1}^{k}E_i$$

- after identififying the best hyperparams, the model is retrained on the full training set and finally evaluated on the test set
- tuning can be expensive !
  - multiplication effect $\to$ expensive computationally

### Optuna for Hyperparameter Tuning

- framework-agnostic $\to$ works with `PyTorch`, `Tensorflow`, `Keras`
- no framework specific syntax $\to$ write standard function
- **lightweight**: minimal computational resources and easy to install
- **versatile**: supports a wide range of ML tasks with various objective functions, multiple search space definitions methods. Several optimization algorithms

#### Optuna's Terminology

- **trial**: a single call of the objective function
  - one set of hyperparams evaluated
- **study**: an optimization seach, a collection of trials
- **parameters**: a variable whose value is to be optimized $\to$ the hyperparam being tuned
- **objective function**: the function that trains, evaluates, and returns the metrics to be optimized
  - loss or accuracy

![Block diagram: Define Objective, which suggests an API to pull values from the search space, trains a model, and returns a performance metric, flows into the objective. The objective flows down into the Optuna Study, which also receives an arrow from Create Study](../../../artifacts/dtb_mlpa_optuna_flow.png)

- Optuna allow dynamic and conditional search space $\to$ define by run approach
- `optuna.create_study()` initializes the optimization task and `study.optimize()` runs N trials against the objective
  - `n_jobs=-1` paralellizes across the driver's node CPU cores
  - scales across cluster: `joblib-Spark` (MLflow Spark Study) or RayTune
- `study.best_params` $\to$ winning hyperparameters
- `study.best_trial` $\to$ full trial record
- `study.best_value` $\to$ objective score
- with Mlflow callback
  - each Optuna trial becomes a child run under a parent run
  - experiments UI stays organized
- Optuna prunes bad trials early $\to$ more wise compute spending
- search space definition
  - `suggest_float()`, `suggest_int()`, `suggest_categorical()`
- sampling strategy $\to$ how to decide the next hyperparameters values
  - continuously refines the search space using past results
- **pruning strategy** $\to$ early stopping halts unpromising trials based on intermediate results
  - `report()` and `should_prune()` after each step to activate pruning

#### Optuna - Mlflow Integration

- efficient tracking of hyperparams and metrics across all Optuna trials
  - `MlflowCallback` from the optuna-integration passt it to `study.optimize()` and every trial is automatically logged as a child MLflow run
  - a parent run groups all trials under a single experiment entry
  - `metric_name` indicates which metric should be tracked
  - `mlflow_kwargs` $\to$ additional arguments to Mlflow
- in Databricks Experiments UI, optuna-mlflow integration organizes each hyperparameter study as a single parent run, with every trial logged as a child run
  - each child run recrods its own hyperparameters and objective metric, while the parent run summarizes the best result
    - easy to compare all trials, review individual trial details, and track the full optimization process
    - reproducibility and governance
- when integrating Optun with Mlflow on Databricks, ensure your `experiment_id` matches an existing MLflow experiment in your workspace
  - robust model governance and deployment use Models in Unity Catalog
    - unified lineage, versioning, and access control for all registered models
