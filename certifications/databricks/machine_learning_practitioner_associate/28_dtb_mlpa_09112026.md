### Overview of Hyperparameter Tuning

#### Ray Ecosystem

- RayCore is a distributed-compute engine, and a family of libraries build on it - each mapping to common workloads
  - **RLib**: Reinforcement Learning
    - autonomous driving (robotics)
    - gaming
    - manufacturing
  - **Tune**: hyperparameter tuning
    - traditional ML - developing DL
    - custom Python optimizations
  - **RayServe**: function serving (not recommended)
  - **RayTrain**: deep learning LLMs
    - ML and DL distributed training
    - alternative to Honovod - GenAI
  - **custom Python**: most types of Python apps
    - finance - HPC-style workloads

- Spark for data, Ray for compute, MLflow for deliver
- the engines are complimentary
  - prepare data with Spark and Delta Lake
  - run the Ray application
  - serve and monitor with MLflow
  - all governed by Unity Catalog

##### Key Concepts of RayTune

- a RayTune job is builti from six pieces
  - **trainable**: function or class RayTune runs once per trial
    - it receives a config of hyperparameters, does the workm and reports a metric back
    - Ray handles the parallelism, checkpointing, and early stopping
    - **function API**: define a function that calls `train.report()` - the common case
    - **class API**: subcalle `tune.Trainable` when you need more flexibility and lifecycle control
    - **auto-checkpointing**: gives state recovery and fault tolerance across distributed actors
    - **early-stopping**: use `tune.stop()` and custom conditions to end unpromising trials early
  - **search space**: defines calid values and selection methods
    - declares wiche hyperparameters to explore an how to sample them
    - keep it lightweight, and use `tune.sample_from` for values that depend on others
    - define it with `Tuner(param_space=...)`
    - avoid large objects in `param_space` - use `tune.with_parameters()` instead
    - use `tune.sample_from(func)` for dependent hyperparameter (only HyperOpt / Optna support conditional spaces)
  - **search algorithm**: efficient strategies for hyperparameter optimization
    - decides which configuration to try next
    - defaults to random search
    - support Bayesian (Ax, BOHB, HyperOpt) and gradient-free (Nevergrad) methods
      - smarter, adaptative search
    - runs in parallel acress CPUs / GPUs for faster tuning
  - **tune schedulers**: stop, pause, or tweak the hyperparameters of running trials
    - manage trials while they run
    - stopping weak ones easrly, pausing and resuming to save resources, or mutating hyperparameters - using metrics
      - with `mode='min` or `max`
    - default: a FIFO scheduler that runs trials in order and does not early stop
  - **trials**: each trial is one experiment run, for one hyperparameter combination
    - `Tuner.fit()` launches, and manages all trials and returns a `ResultGrid()` once they finish
      - runs and manages the tuning
    - requires a trainable and a param space
    - optionally takes tune, runtime, checkpoint and failure configs
    - default behavior:
      - runs untils all trials complete or an error occurs
      - returns a `ResultGrid` to inspect and analyze
  - **analysis**: `Tuner.fit()` returns a `ResultGrid`
    - `ResultGrid` holds everything - per trial logs
      - metrics and checkpoints
      - experiment-level insight
    - pull out the best result, export a DataFrame or plot a metric over time.
