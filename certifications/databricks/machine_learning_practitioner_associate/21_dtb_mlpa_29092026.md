#### Drift Scenarios in Real Life

- **Data Drift**
  - changes in data
    - demographic shift
    - browsing behavior
    - historical sales data
    - promotional activities
  - impacts in data drift
    - **prediction accuracy**: training data no longer represents current behavior and product offerings
    - **sales forecasting**: eco-friendly sales are underestimated while other products are overestimated
  - addressing data drift
    - collect new data
    - retrain the model
    - monitor continuously
- **Concept Drift**
  - an invasive species in crop-yield data changes the relationship between an existing feature - and crop yield, so now the same inputs now map to different outcomes $P(Y|X)$ has changed
    - monitor for new features and changing relationships, retrain when produciton data diverges from training assumptions
- **Bias Drift**
  - production change, introduction of new regional markets with distinct musical preferences alters user demographics and genre popularity
    - monitor group-level performance, retrain and adjust for new populations to maintain fainess and relevance

#### Model Retraining Triggers

1. **Scheduled retraining**
   1. periodic retrainin on a fixed cadence
   2. recommended starting point for production ML
   3. keeps model up-to-date with recent data
2. **Data Changes**
   1. explicit changes in the data can trigger retraining
   2. automated retraining when data drift is detected
   3. ensures model reflects current data patterns
3. **Model Code Changes**
   1. retraining triggered by changes in the model code
   2. often due to concept drift or new features
   3. maintain model relevance and accuracy
4. **Configuration Changes**
   1. alternatives in model configuration can trigger retraining
   2. includes hyperparameters truning and architecture changes
   3. optimizes model performance
5. **Monitoring \& Alerts**
   1. jobs monitor for data and model drift
   2. SQL dashboards displays status and send alerts
   3. automated retraining when drift or degradation is detected

- automatically kick-off a Lakeflow job $\to$ maturity in MLOps practices

#### Monitoring in Machine Learning

- continuous logging and review of key component and system metrics
  - analyze the performance of a solution in production
- why? $\to$ help diagnose issues before they become severe or costly

**Data to Monitor** | **ML Assets to Monitor**
--- | ---
input data (tricky with existing models) | mid-training checkpoints for analysis
data in feature stores and vector databases | component evaluation metrics
human feedback data | ML systems evaluation metrics
model outputs | performance / cost defaults

- fundamentally, it is about early diagnosis
  - log metrics across both data flowing into a system and the ML assets that make it up
  - catch degradation while it is small - before it becomes an expensive production incident
  - data in feature stores and vector databases, especially when it updates frequently

##### Data Profiling Capabilities

###### Metrics, Granularities, Slices \& Assets

- data profiling can be configured from the UI (Unity Catalog Explorer) on the Python API
- **monitor key metrics**: fields such as ``nulls``, ``null%``, `zeros`, `zero%`, `avg`, `distincts`, `distincts%`, `max`, `min`, `stddev`, `median`, `max/min/avg length`, value frequencies, quantiles, and row counts
- **define (multiple) time granularities**: monitor metrics over time windows
- **monitor data slices**: slice metrics based on columns or predicts
- **monitor tables, views, \& ML models**: consistent quality \& drift monitoring of ML production assets - including a machine learning model's fairness and bias
- Python API consists of essentially two calls
  - an idempotent  call to set up (on update) monitoring on a table
  - call to recompute the metrics from the latest contents of the table

```python
# set up monitoring parameters (idempotent - the config for monitoring)
lm.create_monitor(
  table_name="name",
  # ...
)

# refresh monitoring metrics based on the latest contents of the table
lm.run_refresh("name")
```

- for now, call it at the end of the pipeline that writes the table
  - schedule a Lakeflow Jon to run it periodically

##### Databricks SQL Alerts

- periodically run queries, evaluate defined conditions and send notifications if a condition is met
- **scheduled execution:** automatically runs queries at defined intervals to check specific conditions
  - each alert runs independently on its own schedule
- **multichannel notifications**: receive alerts via email, Slack, webhook, MS Teams, PagerDuty
  - facilitating immediate action and response
- a SQL evaluates a trigger condition
  - an agggregate of a value column against an operator and threshold and fires when the condition is met
- set alert schedules trighter than your drift-detection window so an issue is caught within one refresh window
  - point the alert's query at the monitor's drift metrics table rather than raw business table.
